## 1. Что это за проект

Информационная система единой точки входа для студенческих заявлений. Студент
подаёт заявку из приложения, она идёт по маршруту согласования, результат
выдаётся физически через ячейку или фиксируется в системе.

**Ключевой архитектурный принцип** (из ТЗ, раздел 1.1): система — это *один
движок заявок с конфигурируемыми типами*, а не набор независимых модулей. Тип
заявки — это запись конфигурации: схема полей, маршрут, правило доступа, флаги
спецмодулей. Новый тип заводится через админку и работает **без единой правки
кода ядра**. Это главный критерий качества и главный аргумент на защите.

Исходники требований:
- `TZ_full_edinoe_okno.md` — полное ТЗ (копия в репозитории)
- `docs/plan.md` — одобренный план работ
- `design/prototype.dc.html` — кликабельный прототип мобильного клиента
- `design/DESIGN-SYSTEM.md` — брендбук РСО

## 2. Что решено по стеку и почему

| Часть | Технология | Почему так |
|---|---|---|
| Бэкенд | TypeScript, NestJS 10, Prisma 5, PostgreSQL 16, Redis, MinIO | Строго по ТЗ 2.1 |
| Общий код | TypeScript, Zod | Один источник правды для схем и статусной машины |
| Десктоп | Tauri 2 (Rust) + React 18 + Vite + Tailwind | Заказчик попросил **устанавливаемое** приложение для сотрудников |
| iOS | Swift + SwiftUI | Заказчик выбрал натив |
| Android | Kotlin + Jetpack Compose | Заказчик выбрал натив |

Отклонения от ТЗ зафиксированы в `docs/adr/0002-native-clients.md`, в коде
помечены комментарием `// TZ-GAP`.

Главные отклонения:
1. Мобильные клиенты и десктоп вместо адаптивного веба (ТЗ 1.2 их исключало).
2. Refresh-токен не в `httpOnly` cookie, а в защищённом хранилище ОС
   (Keychain / EncryptedSharedPreferences / Tauri store), передаётся в теле
   `POST /auth/refresh`. Ротация сохранена.
3. Канал `PUSH` добавлен к `IN_APP` и `EMAIL`, таблица `device_tokens`.
4. Cron через `@nestjs/schedule`, а не BullMQ — чтобы приложение поднималось
   без Redis. BullMQ вернётся вместе с email-каналом.
5. Параллельные этапы маршрута (`parallel_group`) — расширение сверх ТЗ ради
   обходного листа.

Что это значит на практике: при первом реальном запуске почти наверняка вылезут
ошибки. Ожидаемые места — несоответствие полей Prisma и кода, косяки в raw SQL
(`$queryRaw`), сериализация `BigInt` в `files.sizeBytes`, генерация первой
миграции. На Android — импорты и мелочи Compose.

Юнит-тесты покрывают чистую логику: статусную машину, вычисление `access_rule`,
группы параллельных этапов, лист ожидания, магические байты, разбивку на слоты,
генерацию Zod-схемы формы.

## 6. Как всё запустить

### Бэкенд

```bash
pnpm install
cp .env.example .env   # заполнить JWT_ACCESS_SECRET, JWT_REFRESH_SECRET, SEED_ADMIN_PASSWORD
docker compose up -d
pnpm --filter @edinoe-okno/api prisma:migrate --name init
pnpm --filter @edinoe-okno/api prisma:seed
pnpm dev:api
```

API — `http://localhost:3000/api/v1`, Swagger — `/api/v1/docs`.

**После генерации первой миграции обязательно применить**
`apps/api/prisma/manual/0001_constraints.sql` — там частичный
уникальный индекс броней, GIN по `applications.data`, CHECK периодов и
запрет UPDATE/DELETE на `event_log`. Prisma это декларативно не выражает.

### Интеграционные тесты

```bash
pnpm --filter @edinoe-okno/api test:integration
```

Нужен поднятый Postgres и `DATABASE_URL` в окружении.

### Десктоп

```bash
pnpm --filter @edinoe-okno/desktop dev      # фронт на localhost:1420
pnpm --filter @edinoe-okno/desktop tauri dev # полное приложение, нужен Rust
```

### Android

Открыть `clients/android` в Android Studio. Адрес API в debug —
`http://10.0.2.2:3000/api/v1` (хост-машина с точки зрения эмулятора).

## 8. Грабли, на которые я уже наступил

Чтобы не наступать снова:

1. **`packages/shared` собирается дважды** — CJS для NestJS и ESM для Vite.
   Без ESM-сборки Rollup не видит именованные экспорты через CJS-реэкспорт, и
   десктоп падает на сборке. У десктопа стоят `prebuild` и `predev`, которые
   пересобирают общий код первым. Если добавляешь экспорт в `shared` — пересобери.

2. **Prisma-клиент надо перегенерировать** после каждой правки схемы:
   `pnpm --filter @edinoe-okno/api prisma:generate`.

3. **Puppeteer** ставился с `PUPPETEER_SKIP_DOWNLOAD=1`, браузер докачан
   отдельно: `npx puppeteer browsers install chrome-headless-shell`. В
   `launch()` передаётся `headless: 'shell'`.

4. **Hilt ругается на дубль биндинга**, если класс помечен и `@Inject
   constructor`, и отдаётся через `@Provides`. Уже поймано с `TokenStore`.

5. **Retrofit и значения по умолчанию** у `@Body` — убраны, тело передаётся
   явно из репозитория.

6. **CRLF** — Windows. В репозитории лежит `.gitattributes` с `eol=lf`,
   предупреждения git при коммите можно игнорировать.

## 10. Демо-сценарий для защиты

Тот, который надо отрепетировать, когда всё заработает:

1. Студент открывает каталог, выбирает «Справка об обучении», форма собирается
   по схеме полей, подаёт.
2. Сотрудник деканата видит заявку в очереди, согласовывает первый этап.
3. Сотрудник канцелярии согласовывает второй — движок сам находит свободную
   ячейку, генерирует код получения, переводит заявку в `READY`.
4. Студент видит на телефоне номер ячейки и код.
5. Сотрудник подтверждает выдачу — статус `ISSUED`, ячейка освобождается.
6. Админ открывает журнал событий: все переходы записаны с исполнителем.

**И ключевой момент:** админ создаёт новый тип заявки через редактор — задаёт
поля и маршрут мышкой — студент тут же видит его в каталоге и подаёт. Кода не
трогали. Это и есть доказательство архитектурного принципа.

Дополнительно можно показать обходной лист: пять отделов согласуют
одновременно, финальный этап деканата открывается только когда закрыты все.

## 11. С чего начать в новой сессии

Если ты — я в новой сессии или другой разработчик:

1. Прочитай этот файл и `docs/plan.md`.
2. Проверь, поднимается ли Docker: `docker info`.
3. Если да — раздел 6, поднимай окружение и гоняй интеграционные тесты.
   Это даст первую настоящую обратную связь по бэкенду.
4. Если нет — раздел 7, приоритет 2, там куча работы, не требующей запуска.

Главное, что надо держать в голове: **много кода написано, но мало что
проверено вживую**. Первый настоящий запуск — самая ценная задача из всех
оставшихся.
